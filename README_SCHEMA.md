# Schema reference

Everything Surqlize can declare about a database, and the SurrealQL (SQL) each
declaration generates.

This is a reference for an agent or a developer writing a schema file. It is
exhaustive rather than gentle: every modifier, every option, and the statement it
produces. For the query builder — `select`, `create`, graph traversal, live
queries — see [README.md](README.md). For applying a schema to a database, see
[README_MIGRATIONS.md](README_MIGRATIONS.md).

Every statement shown below was generated by the code in `src/schema/ddl/` and
checked against SurrealDB 3.2.

## The model

One definition is used twice. The same `table(…)` call gives the query builder
its row type and gives the migrator its `DEFINE TABLE`:

```ts
import { t, table } from "surqlize";

export const user = table("user", {
  email: t.string().assert("string::is_email($value)"),
  name: t.string(),
});
```

```surql
DEFINE TABLE user TYPE NORMAL SCHEMAFULL;
DEFINE FIELD email ON TABLE user TYPE string ASSERT string::is_email($value);
DEFINE FIELD name ON TABLE user TYPE string;
```

Two properties follow from this, and both matter when reading the code:

**Schema metadata never changes an inferred type.** `t.string().assert(…)` and
`t.string()` both infer `string`. Constraints live in a separate `ddl` object
hanging off the type (`src/types/ddl.ts`), deliberately apart from it. Only
`t.option(…)` changes what TypeScript sees.

**Every modifier returns a clone.** Types and schemas are shared freely — the
same `t.string()` can be assigned to two fields, and the same table passed to two
`orm()` instances — so nothing is mutated in place:

```ts
const base = t.string();
const email = base.assert("string::is_email($value)");
// `base` is unchanged.
```

Call order does not affect output. Clauses are emitted in the order SurrealQL's
grammar requires, not the order they were written.

## Field types

Built with `t.*`. The middle column is what `printSurqlType()` emits into
`DEFINE FIELD … TYPE`.

| Builder | SurrealQL type | Infers |
|---|---|---|
| `t.string()` | `string` | `string` |
| `t.int()` | `int` | `number` |
| `t.float()` | `float` | `number` |
| `t.decimal()` | `decimal` | `Decimal \| number` |
| `t.number()` | `number` | `number` |
| `t.bool()` | `bool` | `boolean` |
| `t.date()` | `datetime` | `Date` |
| `t.duration()` | `duration` | `Duration` |
| `t.uuid()` | `uuid` | `Uuid` |
| `t.bytes()` | `bytes` | `Uint8Array` |
| `t.any()` | `any` | `unknown` |
| `t.null()` | `null` | `null` |
| `t.none()` | `none` | `undefined` |
| `t.range()` | `range` | `Range<unknown, unknown>` |
| `t.geometry()` | `geometry` | `Geometry` |
| `t.geometry("point")` | `geometry<point>` | `Geometry` |
| `t.record()` | `record` | `RecordId` |
| `t.record("user")` | `record<user>` | `RecordId<"user">` |
| `t.record(["user", "org"])` | `record<user \| org>` | `RecordId<"user" \| "org">` |
| `t.option(t.string())` | `option<string>` | `string \| undefined` |
| `t.array(t.string())` | `array<string>` | `string[]` |
| `t.array(t.string(), 10)` | `array<string, 10>` | `string[]` |
| `t.set(t.string())` | `set<string>` | `string[]` |
| `t.set(t.string(), 10)` | `set<string, 10>` | `string[]` |
| `t.object({ a: t.string() })` | `object` (plus one statement per key) | `{ a: string }` |
| `t.union([t.string(), t.int()])` | `string \| int` | `string \| number` |
| `t.literal("admin")` | `'admin'` | `"admin"` |
| `t.literal(3)` | `3` | `3` |

Notes:

- **Numeric width matters to a migration.** `t.number()` emits `number`, which
  SurrealDB stores as-is; prefer `t.int()`, `t.float()` or `t.decimal()` when the
  column has a width. All three keep `name = "number"` internally so the query
  builder's numeric functions still dispatch on them.
- **Only a maximum is expressible.** `array<string, 1, 10>` is a parse error in
  SurrealDB, so a lower bound has to be an assert:
  `t.array(t.string(), 10).assert("array::len($value) >= 1")`.
- **A tuple has no SurrealQL equivalent.** `t.array([t.string(), t.int()])`
  prints as `array<string | int>` — the closest honest type. TypeScript still
  infers the tuple.
- **Ranges are untyped.** SurrealDB has no `range<T>`.
- **A field is required by its type.** `TYPE string` on a SCHEMAFULL table
  rejects a record that omits the field (`Expected 'string' but found NONE`).
  `.assert("$value != NONE")` is therefore redundant on a non-option field; it is
  harmless, and appears in the examples for readability, but the type is what
  enforces it. Use `t.option(…)` to make a field genuinely optional.

## Field modifiers

Every modifier is available on every type, and they chain. Defined on
`AbstractType` in `src/types/classes.ts`.

| Modifier | Clause | Notes |
|---|---|---|
| `.assert(cond)` | `ASSERT` | Repeatable; joined with `AND` |
| `.default(v)` | `DEFAULT` | Strings that look like expressions are not quoted |
| `.defaultLiteral(s)` | `DEFAULT` | Always quoted, even if it looks like SurrealQL |
| `.defaultAlways(v)` | `DEFAULT ALWAYS` | Re-applied on every update |
| `.valueExpr(expr)` | `VALUE` | Evaluated on write |
| `.computed(expr)` | `VALUE { … }` | Deferred until read |
| `.readonly()` | `READONLY` | Cannot change after creation |
| `.flexible()` | `FLEXIBLE` | Allows values outside the declared type |
| `.permissions(rule)` | `PERMISSIONS` | A raw clause; see below |
| `.comment(text)` | `COMMENT` | |
| `.references(table?)` | `REFERENCE` | The argument is not emitted; see below |
| `.onDelete(action)` | `ON DELETE` | Implies `REFERENCE` on its own |
| `.was(...names)` | *(none)* | Migration metadata only |

Emitted in this fixed order, which SurrealQL's grammar requires:

```
TYPE → FLEXIBLE → DEFAULT → VALUE → READONLY → REFERENCE → ON DELETE
     → ASSERT → PERMISSIONS → COMMENT
```

`FLEXIBLE` before `TYPE` is a parse error; the generator prevents it.

### assert

Repeatable. Several conditions become one clause:

```ts
t.string()
  .assert("string::len($value) >= 2")
  .assert("string::len($value) <= 100")
```

```surql
DEFINE FIELD name ON TABLE user TYPE string
  ASSERT string::len($value) >= 2 AND string::len($value) <= 100;
```

A condition containing a top-level `OR` is parenthesised before joining, because
`AND` binds tighter and joining would otherwise change its meaning. A condition
with no top-level `OR` is left bare: SurrealDB strips redundant parentheses when
it stores a definition, so adding them would make the field look permanently
modified on the next diff.

### default, defaultLiteral, defaultAlways

A string default is ambiguous: `'active'` is data, `time::now()` is code. A
string is treated as an expression when it contains `(`, or starts with `$`, `{`
or `[`. Everything else is quoted.

```ts
t.bool().default(false)                    // DEFAULT false
t.string().default("active")               // DEFAULT 'active'
t.date().default("time::now()")            // DEFAULT time::now()
t.array(t.string()).default([])            // DEFAULT []
t.string().default("it's fine")            // DEFAULT "it's fine"
t.string().defaultLiteral("time::now()")   // DEFAULT 'time::now()'
t.date().defaultAlways("time::now()")      // DEFAULT ALWAYS time::now()
```

Quoting follows SurrealDB's own rule: single quotes, unless the value holds an
apostrophe and no double quote, in which case double. Matching this exactly is
what keeps a declared default equal to the stored one.

`.defaultLiteral()` is the escape hatch for storing characters that happen to
look like code.

### valueExpr and computed

Both store as `VALUE`; the braced form defers evaluation until read.

```ts
createdAt: t.date().valueExpr("time::now()"),
fullName: t.string().computed("string::concat($this.first, ' ', $this.last)"),
```

```surql
DEFINE FIELD createdAt ON TABLE user TYPE datetime VALUE time::now();
DEFINE FIELD fullName ON TABLE user TYPE string
  VALUE { string::concat($this.first, ' ', $this.last) };
```

Named `valueExpr` rather than `value` because `LiteralType` already exposes a
`value` accessor.

`.valueExpr()` overwrites whatever was written; combine it with `.readonly()` for
a created-at stamp, or use `.default()` if the caller should be able to supply
its own.

### references and onDelete

```ts
author: t.record("post").references("post").onDelete("CASCADE"),
```

```surql
DEFINE FIELD author ON TABLE comment TYPE record<post> REFERENCE ON DELETE CASCADE;
```

The referenced table comes from the field's own `record<…>` type, so the argument
to `.references()` is accepted but **not emitted** — `.references("post")` and
`.references()` produce the same statement. `.onDelete(…)` sets `REFERENCE` by
itself, so `.references()` can be left off when an action is given.

`OnDeleteAction` is one of:

| Action | Effect |
|---|---|
| `"CASCADE"` | Delete the referencing record too |
| `"IGNORE"` | Leave the link dangling |
| `"REJECT"` | Block the delete |
| `"UNSET"` | Clear the field |
| `` `THEN ${string}` `` | Run SurrealQL, e.g. `"THEN $this.status = 'orphaned'"` |

These are the only forms SurrealDB 3.2 parses. `SET NULL`, `SET DEFAULT` and
`RESTRICT` — the SQL spellings — are all parse errors.

### permissions

A raw clause, passed through as written:

```ts
secret: t.string().permissions("NONE"),
notes: t.string().permissions("FOR select WHERE published = true"),
```

Unlike the table-level form (below), no `WHERE` is inserted for you here.

### was

Records previous names so a migration carries the value across instead of
dropping the column. It emits nothing into `DEFINE FIELD`; see
[README_MIGRATIONS.md § Renames](README_MIGRATIONS.md#renames).

```ts
nickname: t.option(t.string()).was("handle", "alias"),
```

## Tables

```ts
const user = table("user", { name: t.string() });
```

`table(name, fields)` returns a `TableSchema`. Its modifiers, each returning a
clone:

| Modifier | Clause |
|---|---|
| `.schemafull()` | `SCHEMAFULL` (the default) |
| `.schemaless()` | `SCHEMALESS` |
| `.drop()` | `DROP` — every record written is discarded |
| `.permissions(rules)` | `PERMISSIONS` |
| `.changefeed(duration, includeOriginal?)` | `CHANGEFEED` |
| `.view(select)` | `AS <select>` — a computed view |
| `.comment(text)` | `COMMENT` |
| `.index(name, options)` | a `DEFINE INDEX` statement |
| `.event(name, options)` | a `DEFINE EVENT` statement |

Clause order: `TYPE NORMAL → DROP → SCHEMAFULL|SCHEMALESS → AS → CHANGEFEED →
PERMISSIONS → COMMENT`.

### Permissions

Either one rule for everything, or one per operation:

```ts
table("user", { … })
  .permissions("FULL")

table("user", { … })
  .permissions({
    select: "FULL",
    update: "id = $auth.id",
    delete: "NONE",
  })
```

```surql
DEFINE TABLE user TYPE NORMAL SCHEMAFULL PERMISSIONS FULL;

DEFINE TABLE user TYPE NORMAL SCHEMAFULL
  PERMISSIONS FOR select FULL, FOR update WHERE id = $auth.id, FOR delete NONE;
```

`FULL` and `NONE` stand alone. Anything else is a condition and gets a `WHERE`
prefix if it does not already have one, because a rule reads as a condition and
should be writable as one. (Omitting `WHERE` is otherwise rejected with
`expected 'NONE', 'FULL', or 'WHERE'`.)

Operations not named are left unmentioned, which SurrealDB fills in as `NONE`.

### A worked table

```ts
const user = table("user", {
  email: t.string().assert("string::is_email($value)"),
  name: t.string().comment("Display name"),
})
  .permissions({ select: "FULL", update: "id = $auth.id" })
  .changefeed("3d", true)
  .comment("People");
```

```surql
DEFINE TABLE user TYPE NORMAL SCHEMAFULL CHANGEFEED 3d INCLUDE ORIGINAL
  PERMISSIONS FOR select FULL, FOR update WHERE id = $auth.id COMMENT 'People';
DEFINE FIELD email ON TABLE user TYPE string ASSERT string::is_email($value);
DEFINE FIELD name ON TABLE user TYPE string COMMENT 'Display name';
```

### The injected id

Every table gets an `id` field of type `record<tb>` so the row type has one. It
is **not** emitted as a `DEFINE FIELD` — SurrealDB manages `id` and rejects
`DEFINE FIELD id … TYPE record<tb>` with `not a valid record id key`.

Declaring `id` yourself is different, and is emitted, which is how a table
generates its own ids:

```ts
const doc = table("doc", {
  id: t.uuid().default("rand::uuid::v7()").readonly(),
  body: t.string(),
});
```

```surql
DEFINE FIELD id ON TABLE doc TYPE uuid DEFAULT rand::uuid::v7() READONLY;
```

A declared `id` keeps its position at the head of the field list.

## Edges

A graph edge is a table with `TYPE RELATION`:

```ts
const authored = edge("user", "authored", "post", {
  at: t.date().valueExpr("time::now()"),
});
```

```surql
DEFINE TABLE authored TYPE RELATION IN user OUT post SCHEMAFULL;
DEFINE FIELD at ON TABLE authored TYPE datetime VALUE time::now();
```

`from` and `to` accept an array for an edge that may connect several tables:

```ts
const tagged = edge(["post", "user"], "tagged", "tag", {});
// DEFINE TABLE tagged TYPE RELATION IN post | user OUT tag SCHEMAFULL;
```

Modifiers are the table ones, minus `.drop()` and `.view()`, plus:

| Modifier | Clause |
|---|---|
| `.enforced()` | `ENFORCED` — reject edges whose `in`/`out` record does not exist |

Without `ENFORCED`, SurrealDB will happily create an edge pointing at nothing.

`id`, `in` and `out` are supplied automatically and never emitted as fields —
`in` and `out` come from `TYPE RELATION`. They are present in the row type.

A "one edge per pair" constraint is an index over both endpoints:

```ts
edge("user", "liked", "post", {})
  .index("liked_once", { fields: ["in", "out"], unique: true });
```

## Nested objects and arrays

A schema nests, because that is what produces the row type. SurrealDB does not:
each level is its own statement, and the parent must exist before its children
have anything to attach to.

```ts
table("user", {
  address: t.object({
    street: t.string(),
    city: t.option(t.string()),
  }),
  items: t.array(t.object({ sku: t.string(), qty: t.int() })),
});
```

```surql
DEFINE FIELD address ON TABLE user TYPE object;
DEFINE FIELD address.street ON TABLE user TYPE string;
DEFINE FIELD address.city ON TABLE user TYPE option<string>;
DEFINE FIELD items ON TABLE user TYPE array<object>;
DEFINE FIELD items[*].sku ON TABLE user TYPE string;
DEFINE FIELD items[*].qty ON TABLE user TYPE int;
```

Rules, all in `src/schema/ddl/flatten.ts`:

- Parents are emitted before children.
- Objects inside an array or set are addressed through the element wildcard,
  `items[*].sku`.
- The element field itself (`items[*]`) is **not** emitted. SurrealDB creates one
  for every array automatically, and defining it by hand would show up as an
  extra field on the next diff.
- `option` and array wrappers are looked through to find the object inside, so
  `t.option(t.array(t.object({…})))` still expands.
- A tuple (`t.array([t.string(), t.int()])`) has no single element type, so it is
  not expanded.

## Indexes

```ts
.index(name, options)
```

`IndexOptions`:

| Option | Type | Meaning |
|---|---|---|
| `fields` | `string[]` | Columns to index; omitted only for `count` |
| `unique` | `boolean` | Reject duplicates |
| `fulltext` | `boolean \| FulltextOptions` | Full-text index; exactly one column |
| `hnsw` | `HnswOptions` | Vector index; exactly one column |
| `count` | `boolean` | Index the row count rather than a column |
| `concurrently` | `boolean` | Build without blocking writes |
| `comment` | `string` | |
| `previousNames` | `string[]` | Rename tracking |

Only one of `count`, `hnsw`, `fulltext` and `unique` applies, tested in that
order.

### Plain and unique

```ts
.index("email_idx", { fields: ["email"], unique: true })
.index("post_author", { fields: ["author", "createdAt"] })
```

```surql
DEFINE INDEX email_idx ON TABLE user FIELDS email UNIQUE;
DEFINE INDEX post_author ON TABLE post FIELDS author, createdAt;
```

### Full text

```ts
.index("post_search", {
  fields: ["content"],
  fulltext: { analyzer: "english", highlights: true },
})
```

```surql
DEFINE INDEX post_search ON TABLE post FIELDS content
  FULLTEXT ANALYZER english BM25(1.2,0.75) HIGHLIGHTS;
```

`FulltextOptions`: `analyzer?`, `bm25?` (`true` or `{ k1, b }`), `highlights?`.

`ANALYZER` and `BM25` are always emitted. Both are optional in SurrealQL, but
SurrealDB fills them in and reports them, so a declared index that omitted them
would never converge. Omitting `analyzer` yields the built-in `like`.

**Exactly one column.** SurrealDB rejects more with `Expected one column, found
2`, but only once the statement reaches the server — by which point earlier
statements in the migration have already applied. Surqlize throws at definition
time instead, naming the index.

### Vectors

```ts
.index("embedding_idx", {
  fields: ["embedding"],
  hnsw: { dimension: 1536, dist: "COSINE" },
})
```

```surql
DEFINE INDEX embedding_idx ON TABLE doc FIELDS embedding
  HNSW DIMENSION 1536 DIST COSINE TYPE F32 EFC 150 M 12 M0 24;
```

`HnswOptions`: `dimension` (required), `dist?`, `type?`, `efc?`, `m?`, `m0?`.

Defaults are emitted explicitly, for the same convergence reason: `DIST
EUCLIDEAN`, `TYPE F32`, `EFC 150`, `M 12`, and `M0` at twice `m`.

- `dist`: `COSINE`, `EUCLIDEAN`, `MANHATTAN`, `MINKOWSKI`, `CHEBYSHEV`, `HAMMING`
- `type`: `F64`, `F32`, `I64`, `I32`, `I16`

Also one column only. **MTREE is not supported** — HNSW covers both cases.

### Count

```ts
.index("total", { count: true })
// DEFINE INDEX total ON TABLE user COUNT;
```

### concurrently

Accepted and passed through, but SurrealDB does not store it — it says how to
apply the statement, not what the index is. It is stripped during comparison, so
it never appears in a diff.

## Events

```ts
.event(name, options)
```

`EventOptions`:

| Option | Type | Meaning |
|---|---|---|
| `on` | `"CREATE" \| "UPDATE" \| "DELETE"` or an array | Which operations fire it |
| `when` | `string` | An extra condition, ANDed onto the trigger guard |
| `body` | `string` | The SurrealQL to run (**required**) |
| `comment` | `string` | |
| `previousNames` | `string[]` | Rename tracking |

```ts
.event("set_published_at", {
  on: "UPDATE",
  when: "$before.published = false AND $after.published = true",
  body: "UPDATE $after.id SET publishedAt = time::now()",
})
```

```surql
DEFINE EVENT set_published_at ON TABLE post
  WHEN $event = "UPDATE" AND $before.published = false AND $after.published = true
  THEN UPDATE $after.id SET publishedAt = time::now();
```

How `WHEN` is built:

- `on` becomes a `$event` guard: `$event = "CREATE" OR $event = "UPDATE"`,
  parenthesised when there is more than one.
- `when` is ANDed on, parenthesised only if it contains a top-level `OR` — which
  otherwise would swallow the guard and fire the event on every update matching
  the second half.
- With neither, the clause is `true`, so the event fires on every change.

That last point is the reason `on` is not simply passed through: an empty guard
would produce `WHEN NULL`, which SurrealDB accepts silently and never fires.

`body` is wrapped in braces when it holds more than one statement, or contains
`FOR`, `IF` or `LET`:

```ts
body: "CREATE log SET at = time::now(); UPDATE $after.id SET seen = true"
// THEN { CREATE log SET at = time::now(); UPDATE $after.id SET seen = true }
```

It is named `body` rather than `then` because an object carrying a `then`
property is treated as a thenable by `await`.

## Database-level definitions

Six kinds, each a `DatabaseEntity` that knows how to define and remove itself.
Import from `surqlize` and export them from the schema file alongside the tables.

### analyzer

```ts
analyzer("english", {
  tokenizers: ["blank", "class"],
  filters: ["lowercase", "ascii", "snowball(english)"],
})
```

```surql
DEFINE ANALYZER english TOKENIZERS BLANK, CLASS
  FILTERS LOWERCASE, ASCII, SNOWBALL(ENGLISH);
```

Both lists are uppercased, arguments included, because that is how SurrealDB
stores them. Options: `tokenizers` (required), `filters?`, `comment?`,
`previousNames?`.

### param

```ts
param("rate", { value: "0.2" })
// DEFINE PARAM $rate VALUE 0.2;
```

`value` is a SurrealQL expression, not a JavaScript value. A leading `$` on the
name is stripped, so both spellings work.

### storedFunction

```ts
storedFunction("greet", {
  args: [["name", "string"]],
  returns: "string",
  body: "RETURN 'hi ' + $name;",
})
```

```surql
DEFINE FUNCTION fn::greet($name: string) -> string { RETURN 'hi ' + $name; };
```

Options: `args?` as `[name, surqlType]` pairs, `returns?`, `body` (required,
without the braces), `permissions?`, `comment?`, `previousNames?`.

The `fn::` prefix is added if absent. Note this is the **stored** function, a
database object. It is distinct from `fn(…)` in the ORM, which is a typed
*caller* for one; see [README.md](README.md).

### sequence

```ts
sequence("invoice", { start: 100, batch: 50 })
// DEFINE SEQUENCE invoice BATCH 50 START 100;
```

`BATCH` and `START` are always emitted, defaulting to `1000` and `0`, because
SurrealDB fills them in and a bare definition would look permanently modified.

A sequence's current value is not exposed by `INFO FOR DB`, so dropping and
recreating one silently restarts it. Renaming a sequence is therefore not
supported.

### access

Three types, discriminated on `type`.

**RECORD** (the default) — end users authenticate as rows in a table:

```ts
access("user", {
  signup: "CREATE user SET email = $email, pass = crypto::argon2::generate($pass)",
  signin: "SELECT * FROM user WHERE email = $email AND crypto::argon2::compare(pass, $pass)",
  duration: { token: "15m", session: "12h" },
})
```

```surql
DEFINE ACCESS user ON DATABASE TYPE RECORD
  SIGNUP (CREATE user SET …) SIGNIN (SELECT * FROM user WHERE …)
  DURATION FOR TOKEN 15m, FOR SESSION 12h;
```

Options: `signup?`, `signin?`, `authenticate?`, `duration?`, `comment?`.

**JWT** — trust tokens issued elsewhere:

```ts
access("api", { type: "JWT", url: "https://issuer/.well-known/jwks.json" })
// DEFINE ACCESS api ON DATABASE TYPE JWT URL 'https://issuer/.well-known/jwks.json';

access("api", { type: "JWT", algorithm: "RS256", key: "-----BEGIN PUBLIC KEY-----…" })
// DEFINE ACCESS api ON DATABASE TYPE JWT ALGORITHM RS256 KEY '…';
```

Options: `algorithm?` (defaults `HS512`), `key?`, `issuerKey?`, `url?`. A `url`
replaces `algorithm` and `key`.

**BEARER** — long-lived grants, issued and revoked individually:

```ts
access("keys", { type: "BEARER", for: "RECORD" })
```

```surql
DEFINE ACCESS keys ON DATABASE TYPE BEARER FOR RECORD
  DURATION FOR GRANT 4w2d, FOR TOKEN 1h, FOR SESSION NONE;
```

`for` is `"USER"` or `"RECORD"` and is required. All three durations are always
emitted with SurrealDB's own defaults, again for convergence. The grants
themselves live outside the schema.

**Secrets and re-application.** SurrealDB redacts secrets on read-back — a
signing key comes back as `'[REDACTED]'` — so a definition carrying one can never
equal its stored form. Those definitions are marked `opaque`: created when
missing, then left alone. Re-applying one on every run would rotate the secret
and invalidate whatever was issued under it.

Opaque: `RECORD`, and `JWT` without a `url`.
Compared normally: `BEARER`, and `JWT` with a `url` (nothing is hidden).

The practical consequence: **editing a RECORD access's `signin` query will not
be migrated.** Remove it and re-add it, or apply the change by hand.

**There is no `user()` builder, deliberately.** `DEFINE USER` carries a password
hash, and credentials do not belong in a version-controlled schema file.

### config

```ts
config("GRAPHQL", { tables: ["user", "post"], functions: "NONE" })
// DEFINE CONFIG GRAPHQL TABLES INCLUDE user, post FUNCTIONS NONE;

config("GRAPHQL")
// DEFINE CONFIG GRAPHQL TABLES AUTO FUNCTIONS AUTO;

config("API", { permissions: "FULL" })
// DEFINE CONFIG API PERMISSIONS FULL;
```

`tables` and `functions` take `"AUTO"`, `"NONE"` or a list of names. Both are
always emitted for `GRAPHQL`.

A config is stored without its `DEFINE CONFIG` prefix (`INFO FOR DB` reports
`GRAPHQL TABLES AUTO FUNCTIONS AUTO`) and is keyed under a name matching neither
(`GraphQL`). Both are handled internally.

### Removal statements

For reference, since a migration's `down` uses them:

```surql
REMOVE ANALYZER english;
REMOVE PARAM $rate;
REMOVE FUNCTION fn::greet;
REMOVE SEQUENCE invoice;
REMOVE ACCESS user ON DATABASE;
REMOVE CONFIG GRAPHQL;
```

Note `REMOVE FUNCTION` needs the `fn::` prefix even though `INFO FOR DB` keys the
function without it.

## What a schema file exports

`sur` collects every exported value that looks like a table, an edge or a
database-level definition, from named exports, a default export, or both:

```ts
import { analyzer, edge, t, table } from "surqlize";

export const english = analyzer("english", { tokenizers: ["blank", "class"] });
export const user = table("user", { … });
export const post = table("post", { … });
export const authored = edge("user", "authored", "post", {});

// Optional. A definition exported twice is only migrated once.
export default [english, user, post, authored];
```

Objects and arrays are looked inside, so `export default { user, post }` works
too. A file exporting none of these is an error naming the file.

Order does not matter to the diff, with one exception worth knowing: an analyzer
referenced by a full-text index should exist before the index is built. Declaring
the analyzer in the same schema handles this — database-level definitions are
diffed before tables.

## Generating SurrealQL directly

Everything above is available without a database. All of it is pure string
generation, safe in a browser or a build step.

```ts
import {
  defineField,
  defineSchema,
  defineTable,
  defineEvent,
  defineIndex,
  flattenFields,
  printSurqlType,
} from "surqlize";

defineSchema(user);                       // string[] — table, fields, indexes, events
defineSchema(user, { overwrite: true });  // the same, with DEFINE … OVERWRITE
defineTable(user);                        // string — just the table
printSurqlType(t.option(t.string()));     // "option<string>"
flattenFields(user.fields);               // FlatField[] — one per DEFINE FIELD
```

`{ overwrite: true }` is what a migration uses to modify an existing definition.
SurrealDB has no `ALTER`-based path here: changing a field means redefining it,
because a plain `DEFINE FIELD` on an existing field errors with `The field 'x'
already exists`.

## ER diagrams

```ts
import { mermaid } from "surqlize";

const diagram = mermaid([user, post, authored], { level: "detailed" });
```

Or from the CLI:

```zsh
bun sur mermaid                       # writes schema-diagram.mermaid
bun sur mermaid --level detailed --stdout
bun sur mermaid -o docs/schema.mermaid
```

`MermaidOptions`: `level` (`"minimal"` by default, or `"detailed"`),
`includeComments` (default true, `detailed` only).

```
erDiagram
    post }o--|| user : "author"

    post {
        record id "PK"
        string title "Headline"
        record author
        bool draft "default: true"
    }
```

- Explicit edges are drawn first, then links inferred from `record<…>` fields.
- An edge with several sources or targets draws one arrow per pair.
- Cardinality reflects the field: optional and collection are distinguished
  (`|o--o{` for an optional array, `||--o{` for a required one). A
  self-reference is always drawn one-to-many.
- `id`, `in` and `out` are never read as links.
- `UK` comes from a unique index covering the field; `PK` from the name `id`.
- Types are simplified for display — `float` and `decimal` read as `number`,
  `uuid` and `duration` as `string`, `array<…>` as `array`.
- Dotted paths become underscored in entity rows (`address_street`), because
  Mermaid's attribute token accepts only word characters. Relationship labels
  keep the dots.
- `detailed` adds defaults, `readonly`, computed markers, summarised constraints
  and comments as one quoted blob.

## Rules SurrealDB imposes

Worth knowing before writing a schema, because none of them are obvious and most
were found the hard way. The full account, with a reproducible probe script, is
in [SURREALDB-FINDINGS.md](SURREALDB-FINDINGS.md).

| Rule | Consequence |
|---|---|
| No `RENAME` statement | `.was()` is generated as a four-statement data migration |
| Tables cannot be renamed | Record IDs embed the table name; inbound links would dangle |
| Full-text and HNSW take one column | Define one index per column |
| `array<T, min, max>` is a parse error | Only a maximum; a minimum is an assert |
| No `range<T>` | Ranges are untyped |
| `DEFINE FIELD id … TYPE record<tb>` is rejected | The injected `id` is never emitted |
| `FLEXIBLE` must follow `TYPE` | Clause order is fixed by the generator |
| A permission rule needs `WHERE` | Added for you at table level, not at field level |
| `WHEN NULL` events are accepted and never fire | `on` always produces a real guard |
| Secrets read back as `[REDACTED]` | Opaque definitions are created once, never updated |
| `REMOVE FIELD` leaves dependent indexes | A `UNIQUE` index can silently stop enforcing |
| Sequence position is not introspectable | Sequences cannot be renamed |
| SurrealDB fills in omitted defaults | Index and access defaults are emitted explicitly |

## A complete example

From `examples/blog.ts`, which is migrated against a live server in CI. Five more
sit alongside it: `minimal`, `social-network`, `social-platform`, `ecommerce` and
`ai-embeddings`.

```ts
import { analyzer, edge, t, table } from "surqlize";

export const english = analyzer("english", {
  tokenizers: ["blank", "class"],
  filters: ["lowercase", "ascii", "snowball(english)"],
});

export const user = table("user", {
  email: t.string().assert("string::is_email($value)"),
  name: t.string().assert("string::len($value) >= 2"),
  bio: t.option(t.string()),
  isActive: t.bool().default(true),
  createdAt: t.date().valueExpr("time::now()"),
})
  .index("user_email", { fields: ["email"], unique: true })
  .index("user_active", { fields: ["isActive"] });

export const post = table("post", {
  author: t.record("user"),
  title: t.string().assert("string::len($value) <= 200"),
  slug: t.string(),
  content: t.string(),
  tags: t.array(t.string()).default([]),
  published: t.bool().default(false),
  publishedAt: t.option(t.date()),
  viewCount: t.int().default(0),
  createdAt: t.date().valueExpr("time::now()"),
})
  .index("post_slug", { fields: ["slug"], unique: true })
  .index("post_author", { fields: ["author", "createdAt"] })
  // Full-text takes exactly one column.
  .index("post_search", { fields: ["content"], fulltext: { analyzer: "english" } })
  .event("set_published_at", {
    on: "UPDATE",
    when: "$before.published = false AND $after.published = true",
    body: "UPDATE $after.id SET publishedAt = time::now()",
  });

/** One like per user per post, enforced by the index. */
export const liked = edge("user", "liked", "post", {
  likedAt: t.date().valueExpr("time::now()"),
}).index("liked_once", { fields: ["in", "out"], unique: true });

export default [english, user, post, liked];
```

```zsh
bun sur plan    --schema examples/blog.ts
bun sur migrate --schema examples/blog.ts
```
